# Rustらしいパフォーマンス最適化アーキテクチャ移行計画

## 1. 概要

本ドキュメントは、`docs/develop/architecture/rust_optimized_architecture.md` で定義した設計方針を実装へ落とし込むための具体的な進行計画をまとめます。アーキテクチャ上の判断や責務分担は設計書側を参照してください。

## 2. フェーズ別アクション

### Phase 1: 基盤整備（1-2日想定）

- thiserror クレートの追加と `AppError` 実装
- Configuration モジュールの作成
- `AppState` の実装

### Phase 2: コア機能の移行（2-3日想定）

- Repository 層の最適化（借用ベース API への置換）
- Facade 層の `AppState` 対応
- `main.rs` の初期化処理更新

### Phase 3: Builder Pattern 導入（1-2日想定）

- `BattleRecruitmentBuilder` の実装
- 他 Builder（必要に応じて）の実装
- プレゼンテーション層の Builder 利用コードへ更新

### Phase 4: 最適化・テスト（2-3日想定）

- パフォーマンステストの実施
- ユニットテスト／統合テストの整備
- ドキュメント更新（設計書・ユーザー向け資料の確認含む）

## 3. テスト計画

- Phase 2 完了後に主要サービス／Facade のユニットテストを追加し、`mockall` を用いた依存差し替えを確認する。
- Phase 3 完了後に Builder 利用を通した end-to-end テスト（プレゼンテーション → Facade → Service → Repository）を実施する。
- Phase 4 ではベンチマークシナリオ（募集作成・更新フロー）を定義し、変更前後で CPU／メモリ使用量と応答時間を比較する。

## 4. リスクと対策

- **依存関係のすり替え漏れ**: フェーズ完了ごとに `AppState` からの依存注入が行われているかを静的解析（`cargo clippy`）とコードレビューで確認する。
- **Builder API の破壊的変更**: 公開インターフェースの変更時はコマンドハンドラ側の修正一覧を管理し、マイグレーション手順を `docs/develop/features` に反映する。
- **パフォーマンス劣化**: ベンチマーク結果を記録し、目標値を下回る場合は `Arc` 利用箇所と非同期処理の粒度を見直す。

## 5. 進捗管理

- 各フェーズ終了時に本計画書を更新し、完了チェックと新規課題を追記する。
- 設計方針に変更が生じた場合は設計書を先に更新し、本計画の関連箇所を同期させる。
