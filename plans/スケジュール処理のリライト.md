# スケジュール処理のリライト

## 背景

現在のスケジュール処理は`notifications`テーブルベースで通知処理しか対応できていない。
今後、下記の機能が追加される予定であり、より汎用的なスケジュール処理が必要となる。

- **解散機能**: マルチ募集で指定時刻にメンバーが集まらない場合に自動解散
- **定期募集機能**: 既に実装済みだが、現在は独立した処理として動作
- **データ整理機能**: 定期的にDBの古いデータを削除（AM3〜5時に実行）

現在は`SchedulerFacade::execute_notifications()`内で通知と定期募集を別々に呼び出しているが、
これらを統一的なスケジュール処理の枠組みで扱えるようにリライトする。

## 現状の実装の確認

### 処理フロー（10秒間隔）

1. `ScheduleNotificationTimer::start()` - 10秒間隔でタイマー起動
2. `SchedulerFacade::execute_notifications()` - 通知と定期募集を実行
   - 通知処理: `NotificationService::execute_scheduled_notifications()`
   - 定期募集処理: `SchedulerFacade::execute_recruitment_schedules()`
3. `last_process_times`テーブルを更新

### 既存の仕組みの特徴

- **Bot停止対応**: `last_process_times.execute_time`から現在時刻までの範囲で処理を行う
  - Bot停止中に実行すべきだったスケジュールも後で実行される
- **トランザクション管理**: Facade層でトランザクション境界を管理
- **重複実行防止**:
  - 通知: `is_sent`フラグで管理
  - 定期募集: `last_process_times`で管理（同じ募集時間は1度しか作成されない）

### 現在の処理種別（LastProcessType）

```rust
pub enum LastProcessType {
    Schedule = 1,                      // 通知スケジュール
    SpreadsheetLoad = 2,               // スプレッドシート読み込み
    SpreadsheetPush = 3,               // スプレッドシート書き込み
    BattleRecruitmentSchedule = 4,     // 定期募集
}
```

## 要求仕様

### 守るべきこと

1. **既存の通知処理を踏襲**
   - Botが停止しても後で通知を行うよう`last_process_times.execute_time`から逆算して処理
   - トランザクション管理はFacade層で行う
   - エラー時のロールバックとリトライ機能を維持

2. **汎用的なスケジュール処理**
   - スケジュールループの中で処理区分（通知、解散、定期募集、データ整理など）に分岐
   - 各区分に応じた処理を実行

3. **拡張性**
   - 新しいスケジュール処理種別を簡単に追加できる設計

## 設計方針

### スケジュールテーブルの統一 + 関連テーブル方式（推奨）

#### 設計思想

- **パフォーマンス重視**: JSONBではなく専用テーブルでインデックスを活用
- **型安全性**: Rust側で厳密な型チェックが可能
- **既存資産の活用**: `notifications`テーブルを拡張して使用
- **保守性**: タスク種別ごとに明確なデータ構造を持つ
- **スケジューラー**: tokio-cron-schedulerを採用（ただしcrate自体のpersistence機能は使用せず、独自のテーブルを使用）
- **整合性優先**: 実行時のDB再確認により、タスク変更・削除に対する整合性を保証

#### データモデル

##### `scheduled_tasks`テーブル（新規作成）

すべてのスケジュール処理の基底テーブル

```sql
CREATE TABLE worker.scheduled_tasks (
    id SERIAL PRIMARY KEY,
    schedule_datetime TIMESTAMPTZ NOT NULL,  -- 実行日時
    task_type INT NOT NULL,                  -- タスク種別（1:通知, 2:解散, 3:データ整理）
    guild_id BIGINT,                         -- ギルドID（NULL可、全体処理の場合）
    channel_id BIGINT,                       -- チャンネルID（NULL可）
    is_executed BOOLEAN NOT NULL DEFAULT FALSE,  -- 実行済みフラグ
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_scheduled_tasks_datetime_not_executed
    ON worker.scheduled_tasks(schedule_datetime)
    WHERE is_executed = false;  -- 未実行タスクに特化した部分インデックス
CREATE INDEX idx_scheduled_tasks_type ON worker.scheduled_tasks(task_type);
CREATE INDEX idx_scheduled_tasks_guild ON worker.scheduled_tasks(guild_id);
```

##### タスク種別の定義

```rust
pub enum ScheduledTaskType {
    Notification = 1,              // 通知
    Dissolution = 2,               // 解散
    DataCleanup = 3,               // データ整理
}
```

**Note**: 定期募集は設定ベースの処理なので、タスク種別には含めない。

##### 既存テーブルとの関係と関連テーブル

**1. 通知タスク（task_type=1）**

#### 処理フロー（tokio-cron-scheduler統合型）

##### スケジューラー初期化（Bot起動時）

```
SchedulerManager::initialize()
  ↓
  ├─ tokio-cron-schedulerの初期化
  │   └─ crate自体のpersistence機能は使用しない（独自テーブルで管理）
  │
  ├─ [過去の未実行タスク処理] Bot停止中に実行されるべきだったタスクを実行
  │   ├─ last_process_times.execute_time取得
  │   ├─ execute_time ~ now の範囲で未実行タスクを取得
  │   │   - notifications (is_sent=false)
  │   │   - scheduled_tasks (is_executed=false)
  │   └─ 各タスクを順次実行（実行前にDB再確認）
  │
  ├─ last_process_timesを現在時刻に更新
  │
  └─ [プリロードジョブ登録] 10秒間隔でプリロード処理を実行
      └─ "*/10 * * * * *" (10秒ごと)
```

##### プリロード処理（10秒間隔）

```
SchedulerManager::preload_tasks()
  ↓
  ├─ now ~ now+20秒 の範囲でタスクを取得
  │   ├─ notifications (is_sent=false)
  │   └─ scheduled_tasks (is_executed=false, task_type別)
  │
  └─ 各タスクについてtokio-cron-schedulerにジョブを登録
      └─ schedule_datetime の正確な時刻に実行されるよう設定
```

##### タスク実行時（schedule_datetimeに到達）

```
TaskExecutor::execute(task_id)
  ↓
  ├─ [実行時DB再確認] DBから最新のタスク状態を取得
  │   ├─ タスクが削除されている → スキップ
  │   ├─ タスクが既に実行済み → スキップ
  │   └─ タスクが有効 → 実行続行
  │
  ├─ タスク種別に応じた処理を実行
  │   ├─ [通知処理] NotificationService::execute_notification()
  │   ├─ [解散処理] DissolutionTaskExecutor::execute()
  │   ├─ [データ整理処理] DataCleanupTaskExecutor::execute()
  │   └─ [定期募集処理] RecruitmentScheduleService::execute_recruitment()
  │
  └─ is_sent / is_executed フラグを更新
```

##### 全体統括（SchedulerFacade）

```
SchedulerFacade::execute_all_schedules()
  ↓
  ├─ プリロード処理の実行（10秒間隔で自動呼び出し）
  │
  └─ [定期募集処理] 独立処理として実行（設定ベースの動的生成）
      └─ RecruitmentScheduleService::execute_recruitment_schedules()
          - battle_recruitment_schedulesから有効な設定を取得
          - 募集作成時にnotificationsと解散タスク（scheduled_tasks）を同時作成
```

#### メリット

- **パフォーマンス**: インデックスが効き、検索・更新が高速
  - `recruit_id`で解散タスクを検索可能（募集修正時に解散タスクも更新）
  - 部分インデックス活用で未実行タスクの検索を最適化
  - プリロード戦略（10秒間隔、20秒先読み）によりDB負荷を低減
- **正確性**: tokio-cron-schedulerにより秒単位の正確なタイミングで実行
  - 従来の10秒間隔ポーリングより高精度
- **整合性**: 実行時のDB再確認により、タスク変更・削除に確実に対応
  - キャッシュ無効化などの複雑な仕組み不要
  - Bot停止・再起動にも対応（last_process_times活用）
- **型安全性**: Rust側で厳密な型チェックが可能
- **既存資産の活用**: `notifications`テーブルをそのまま使用（マイグレーション不要）
- **保守性**: タスク種別ごとに明確なデータ構造
- **コスト効率**: JSON解析のオーバーヘッドがない

#### デメリット

- **テーブル数の増加**: タスク種別ごとに関連テーブルが必要
  - ただし、パフォーマンスとのトレードオフとして許容範囲
- **コードの複雑性**: タスク種別ごとに異なるテーブルをJOIN
  - ただし、Repositoryパターンで抽象化すれば影響は限定的

1. **SchedulerManager作成**

2. **プリロード処理の実装**
   ```rust
   async fn preload_tasks(&self) -> Result<()> {
       let now = Utc::now();
       let to = now + Duration::seconds(20);

       // notifications取得
       let notifications = self.notification_service
           .find_pending_in_range(now, to).await?;

       // scheduled_tasks取得
       let tasks = self.scheduled_task_service
           .find_tasks_in_range(now, to).await?;

       // 各タスクをtokio-cron-schedulerに登録
       for notification in notifications {
           self.scheduler.add_once(notification.schedule_datetime, move || {
               self.execute_notification(notification.id)
           }).await?;
       }

       for task in tasks {
           self.scheduler.add_once(task.schedule_datetime, move || {
               self.execute_task(task.id, task.task_type)
           }).await?;
       }

       Ok(())
   }
   ```

3. **実行時DB再確認ロジック**
   ```rust
   async fn execute_task(&self, task_id: i32, task_type: ScheduledTaskType) -> Result<()> {
       // DB再確認
       let task = match self.scheduled_task_service.get_task_by_id(task_id).await? {
           Some(t) if !t.is_executed => t,
           _ => {
               debug!(task_id, "タスクは既に実行済みまたは削除されています");
               return Ok(()); // スキップ
           }
       };

       // タスク種別に応じた処理
       match task_type {
           ScheduledTaskType::Dissolution => {
               self.dissolution_executor.execute(task_id).await?;
           }
           ScheduledTaskType::DataCleanup => {
               self.data_cleanup_executor.execute(task_id).await?;
           }
           _ => {}
       }

       Ok(())
   }
   ```

4. **Bot起動時の過去タスク処理**
   ```rust
   async fn initialize(&self) -> Result<()> {
       let now = Utc::now();
       let last_execute_time = self.scheduler_service
           .get_last_process_time(LastProcessType::Schedule)
           .await?
           .and_then(|lpt| lpt.execute_time);

       // 過去の未実行タスクを取得・実行
       if let Some(last_time) = last_execute_time {
           let past_notifications = self.notification_service
               .find_pending_in_range(last_time, now).await?;
           let past_tasks = self.scheduled_task_service
               .find_tasks_in_range(last_time, now).await?;

           for notification in past_notifications {
               self.execute_notification(notification.id).await?;
           }

           for task in past_tasks {
               self.execute_task(task.id, task.task_type).await?;
           }
       }

       // last_process_timesを現在時刻に更新
       self.scheduler_service.update_last_process_time(
           LastProcessType::Schedule,
           now
       ).await?;

       // プリロードジョブを登録（10秒間隔）
       self.scheduler.add_cron("*/10 * * * * *", || {
           self.preload_tasks()
       }).await?;

       Ok(())
   }
   ```

## 解散機能の詳細設計

### 解散タスクの作成タイミング

マルチ募集コマンド実行時、または定期募集作成時に解散日時が指定された場合:

1. `battle_recruitments`レコード作成
2. 各解散日時（最大3つ）に対して下記を作成:
   - `scheduled_tasks`レコード作成
     - `task_type = 2`（Dissolution）
     - `schedule_datetime = 解散日時`
     - `guild_id = 募集のギルドID`
     - `channel_id = 募集のチャンネルID`
   - `scheduled_task_dissolutions`レコード作成
     - `task_id = 上記で作成したタスクID`
     - `recruit_id = 募集ID`

### DissolutionTaskExecutorの処理内容

1. `scheduled_tasks`と`scheduled_task_dissolutions`をJOINして実行対象を取得
2. 各解散タスクについて:
   - `recruit_id`から募集情報を取得
   - `recruitment_participants`から参加者数を取得
   - **必要人数に達していない場合**:
     - 募集をキャンセル（`battle_recruitments.is_canceled=true`）
     - 解散メッセージを送信（`message_text_id`を使用）
     - 関連する通知タスクと他の解散タスクも無効化
   - **必要人数に達している場合**:
     - 何もしない（正常に募集成立）
   - `scheduled_tasks.is_executed=true`に更新

### 募集修正時の対応

募集情報（開始日時、解散日時など）が修正された場合:

1. `recruit_id`で`scheduled_task_dissolutions`を検索
2. 既存の解散タスクを削除（`scheduled_tasks`もCASCADEで削除）
3. 新しい解散日時で解散タスクを再作成

**パフォーマンス**: `recruit_id`にインデックスがあるため高速検索可能

## 定期募集機能の統合

### 現在の実装

- `battle_recruitment_schedules`テーブルで定期募集設定を管理
- `SchedulerFacade::execute_recruitment_schedules()`で曜日・時刻を計算して募集作成

### 統合後の設計

定期募集は**設定ベース**の処理として独立して維持し、`scheduled_tasks`には含めない。

**理由**:
- 定期募集は「毎週月曜22時」のような**繰り返しルール**であり、個別のスケジュールタスクではない
- 動的に募集日時を計算する必要があるため、事前にタスク化できない

**処理フロー**:
1. `execute_recruitment_schedules()`で次回募集日時を計算
2. 募集作成時に`battle_recruitments`と同時に下記を作成:
   - **通知タスク**: `notifications`テーブル（既存の仕組みを活用）
   - **解散タスク**: `scheduled_tasks`（task_type=2）+ `scheduled_task_dissolutions`（解散設定がある場合）

**定期募集に解散設定を追加する場合のテーブル設計**:

```sql
-- battle_recruitment_schedulesテーブルに解散設定を追加（将来拡張）
ALTER TABLE guild_master.battle_recruitment_schedules
ADD COLUMN dissolution_settings JSONB;  -- 解散日時の設定（例: ["1時間前", "30分前"]）
```

これにより、定期募集は**タスク生成元**として機能し、生成されたタスク（通知・解散）は各テーブルで管理される。

## データ整理機能の統合

### 要件（plans/定期的にデータの整理を行う.md）

- **削除対象**: `battle_recruitments`（クエスト開始日時が過去）、`notifications`（通知済み）
- **実行時間**: AM3〜5時

### 実装方針

#### データ整理タスクの作成

1. **初回起動時またはスケジュール生成時**
   - 次のAM3〜5時の間でランダムな時刻を計算（例: AM3:27）
   - `scheduled_tasks`にデータ整理タスクを作成
     - `task_type = 4`（DataCleanup）
     - `schedule_datetime = 次のAM3:27（UTC）`
     - `payload = {"target_tables": ["battle_recruitments", "notifications"]}`

2. **実行後**
   - 次の日のAM3〜5時のタスクを自動作成（繰り返し実行のため）

#### DataCleanupTaskExecutorの処理内容

1. `last_process_times.execute_time`より前のデータを削除
   - `battle_recruitments`: `quest_start_at < last_process_times.execute_time`
   - `scheduled_tasks`: `is_executed=true AND schedule_datetime < last_process_times.execute_time`
2. 削除件数をログ出力
3. 次回実行タスクを作成

## last_process_timesの扱い

### 現状

- `Schedule = 1`: 通知処理の最終実行時刻
- `BattleRecruitmentSchedule = 4`: 定期募集処理の最終実行時刻

### リライト後

#### 統合案（推奨）

`Schedule`に統一し、すべてのスケジュール処理の最終実行時刻を管理:

```rust
pub enum LastProcessType {
    Schedule = 1,                      // 全スケジュール処理（通知・解散・定期募集・データ整理）
    SpreadsheetLoad = 2,
    SpreadsheetPush = 3,
    // BattleRecruitmentSchedule = 4,  // 削除（Scheduleに統合）
}
```

**理由**:
- 通知・解散・定期募集・データ整理のすべてが同一タイミング（10秒間隔）で実行される
- 実行時刻を統一管理することで、Bot停止時の処理漏れを防ぐ
- 定期募集も`Schedule`の一部として扱うことで、処理の一貫性が保たれる

#### 処理フロー

1. `last_process_times`から`Schedule`の`execute_time`を取得
2. `execute_time`から現在時刻までの範囲で下記を実行:
   - 通知タスク（`notifications`）
   - 解散タスク（`scheduled_tasks` task_type=2）
   - データ整理タスク（`scheduled_tasks` task_type=3）
   - 定期募集処理（動的計算による募集作成）
3. すべてのタスク実行後、`execute_time`を現在時刻に更新

**マイグレーション**:
- `BattleRecruitmentSchedule`の最終実行時刻を`Schedule`にマージ
- 2つの時刻のうち、古い方を採用（処理漏れを防ぐため）

## リスクと対策

### リスク1: テーブルの複雑性増加

**リスク内容**:
- タスク種別ごとに関連テーブルが必要となり、テーブル数が増加
- JOIN処理が複雑化する可能性

**対策**:
- Repositoryパターンで抽象化し、JOIN処理を隠蔽
- 各Repositoryが適切なデータ構造を返すようにする
- 例: `DissolutionRepository::find_pending_tasks()` → `Vec<(ScheduledTask, Dissolution)>`

### リスク2: 既存機能への影響

**リスク内容**:
- 通知処理の変更により既存機能が影響を受ける可能性

**対策**:
- 通知処理（`NotificationService`）は変更しない
- 新しい処理（解散、データ整理）を追加するのみ
- 既存のテストケースを維持
- 十分なログ出力とモニタリング

### リスク3: last_process_timesの統合による影響

**リスク内容**:
- `BattleRecruitmentSchedule`を削除することで、定期募集の処理履歴が失われる

**対策**:
- マイグレーション時に両方の時刻を比較し、古い方を`Schedule`に設定
- 処理漏れを防ぐため、保守的なアプローチを取る
- マイグレーション前後でログを比較し、処理回数を確認

### リスク4: パフォーマンス劣化

**リスク内容**:
- 複数のテーブルにまたがる処理により、パフォーマンスが劣化する可能性

**対策**:
- 適切なインデックスを設定（特に`recruit_id`, `schedule_datetime`, `is_executed`）
- 部分インデックスを活用（`WHERE is_executed = false`）
- 実行対象のタスク数が多い場合はバッチ処理を検討
- クエリのEXPLAIN ANALYZEで実行計画を確認

## まとめ

本計画では、パフォーマンスとコストを重視し、下記の設計方針でスケジュール処理をリライトする:

### 主要な設計決定

1. **既存テーブルの活用**: `notifications`テーブルは変更せず、そのまま通知処理に使用
2. **関連テーブル方式**: JSONBではなく、タスク種別ごとに専用の関連テーブルを作成
3. **インデックス最適化**: `recruit_id`、`schedule_datetime`、`is_executed`に適切なインデックスを設定
4. **tokio-cron-scheduler採用**: 高精度なタイミング制御（ただしcrate自体のpersistence機能は不使用）
5. **プリロード戦略**: 10秒間隔で20秒先までのタスクを先読みし、メモリとDB負荷のバランスを取る
6. **実行時DB再確認**: タスク実行前にDBから最新状態を取得し、変更・削除に対する整合性を保証
7. **Bot停止対応**: 起動時に過去の未実行タスクを優先処理し、処理漏れを防止

### 得られるメリット

- **パフォーマンス**: インデックスが効き、検索・更新が高速（特に募集修正時の解散タスク更新）
- **正確性**: tokio-cron-schedulerにより秒単位の正確なタイミングで実行（従来の10秒間隔ポーリングより高精度）
- **整合性**: 実行時DB再確認により、タスク変更・削除に確実に対応（キャッシュ無効化不要）
- **型安全性**: Rust側で厳密な型チェックが可能
- **保守性**: タスク種別ごとに明確なデータ構造
- **コスト効率**: JSON解析のオーバーヘッドがなく、CPU使用率を低減
- **拡張性**: 新しいタスク種別を追加する際も、専用テーブルを追加するだけ

### 既存の仕組みの維持

- **Bot停止対応**: `last_process_times.execute_time`から現在時刻までの範囲で処理
- **トランザクション管理**: Facade層でトランザクション境界を管理
- **重複実行防止**: `is_sent`（通知）、`is_executed`（解散・データ整理）フラグで管理

既存の通知処理の仕組みは維持しつつ、パフォーマンス、コスト、整合性を重視した汎用的なスケジュール処理基盤を構築する。
