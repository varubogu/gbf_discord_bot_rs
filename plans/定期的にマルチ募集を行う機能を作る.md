毎日コマンドを打ってマルチ募集するのは面倒
そこで自動的に募集を立ててくれる機能を作成する

## 概要

- 毎日指定時間にマルチ募集を立てる
- その情報はDBとスプレッドシートで管理する
- 登録はguild単位。

## スプレッドシートの仕様

- テーブル名：マルチ募集スケジュール（guild_master.battle_recruitment_schedules）
- カラム：
  - id: uuidv4
  - day_of_week：曜日（月、火、水、木、金、土、日、毎日）から任意の数をカンマ区切りで入力
  - recruit_start_day: 行く日の何日前に募集するか（0は当日、1で前日、2で二日前）
  - recruit_start_time: 上記日付の何時に募集するか（省略可、省略時はquest_start_timeの時刻）
  - start_time：開始時間（hh:mm）
  - quest_id：クエスト（クエストID）
  - battle_style_id：攻略方法（バトル種類ID）※オプション


## DBの仕様

- テーブル名：マルチ募集スケジュール（guild_master.battle_recruitment_schedules）
- カラム：
  - id: ID(uuidv4)
  - recruit_start_day: (int)行く日の何日前に募集するか（0は当日、1で前日、2で二日前）
  - recruit_start_time: (str)上記日付の何時に募集するか（省略可、省略時はquest_start_timeの時刻）
  - quest_start_time：(str)開始時間（hh:mm）
  - quest_id： (int)クエスト（クエストID）
  - battle_style_id：(int)攻略方法（バトル種類ID）※オプション

- テーブル名：マルチ募集スケジュール対象曜日（guild_master.battle_recruitment_schedules_day_of_week）
- カラム：
  - id: ID(uuidv4)
  - day_of_week：(int)曜日の数値
    - 0: 毎日
    - 1: 月
    - 2: 火
    - 3: 水
    - 4: 木
    - 5: 金
    - 6: 土
    - 7: 日

## どのように処理するか？

まず通知処理のためのイベントループを仕様変更し、区分ごとに処理が動くように汎用化する
例えば
バッチ処理:1
イベントスケジュール通知処理:2
マルチバトル募集5分前通知処理:3
マルチバトル募集時刻通知処理:4
マルチバトル定期募集登録:5
のように区分を用意

それぞれにあった関数が呼び出されて処理される。

1〜4は今まで通り
5は新規処理でマルチバトル定期募集関連のテーブルを見てマルチバトル情報を登録しにいく
募集開始以後はユーザーがスラッシュコマンドで実行したときと同じ動作をする。

## 操作権限

全ユーザー登録・解除可能
自分で登録したもののみ解除可能だが人のものは解除できない
ただしbotコントロール権限を持つユーザーは他の人のも削除できる

### 2. 処理フロー設計

#### 2.1 定期募集登録処理

**実行タイミング**: 10秒間隔のスケジュール通知タイマー内で実行

**処理フロー**:

```
1. last_process_timesから前回実行時刻を取得（LastProcessType::BattleRecruitmentSchedule）
2. 現在時刻を取得
3. 有効なスケジュール（is_enabled=true）を全取得
4. 各スケジュールについて:
   a. 対象曜日を取得
   b. 前回実行時刻から現在時刻までの間に該当する募集開始日時を計算
   c. 既に登録済みの募集がないかチェック（重複防止）
   d. 未登録の場合、battle_recruitmentsに登録
   e. マルチ募集メッセージを投稿（既存の募集投稿ロジックを再利用）
   f. 開始時刻の通知が必要な場合、notificationsテーブルに登録
5. last_process_timesを現在時刻で更新（LastProcessType::BattleRecruitmentSchedule）
```

**重複チェックロジック**:
- 同一guild_id、channel_id、quest_id、quest_start_at（日時）の組み合わせで既存レコードを検索
- 存在する場合はスキップ

#### 2.2 募集日時の計算ロジック

**例**:
- クエスト開始時刻: 毎週水曜日 22:00
- 募集開始日オフセット: 1（前日）
- 募集開始時刻: 20:00

→ 毎週火曜日 20:00 に募集を投稿

**計算手順**:
1. 現在日時から次回のクエスト開始日時を計算
2. recruit_start_day_offsetを適用して募集開始日を算出
3. recruit_start_timeが指定されていればその時刻、なければquest_start_timeを使用
4. 計算された募集開始日時が前回実行時刻と現在時刻の範囲内にあるかチェック

### 3. アーキテクチャ設計

#### 3.1 層別責務

**Repository層** (`repository/database/schedule/battle_recruitment_schedule_repository.rs`):
- `find_all_enabled_schedules_with_days()`: 有効な全スケジュールと曜日情報を取得
- `find_by_guild_id()`: ギルドIDでスケジュール取得
- `find_by_created_by()`: 作成者IDでスケジュール取得
- `create_with_txn()`: スケジュールと曜日を作成（トランザクション使用）
- `update_with_txn()`: スケジュール更新
- `delete_with_txn()`: スケジュール削除（CASCADE により曜日も削除）
- `toggle_enabled_with_txn()`: 有効/無効の切り替え

**Service層** (`services/schedule/recruitment_schedule_service.rs`):
- `calculate_next_recruitment_times()`: 次回募集日時の計算
- `check_duplicate_recruitment()`: 重複チェック
- `validate_schedule_input()`: 入力値のバリデーション（曜日の重複、時刻の妥当性など）

**Facade層** (`facades/scheduler.rs`に追加):
- `execute_recruitment_schedules()`: 定期募集の実行とトランザクション管理
  - スケジュール取得
  - 募集日時計算
  - 重複チェック
  - 募集作成（battle_recruitmentsへのINSERT + Discordメッセージ投稿）
  - 通知登録（必要な場合）
  - last_process_times更新
  - トランザクションのcommit/rollback

**Event層** (`events/interactions/command_interactions/slash/`):
- `recruitment_schedule_create.rs`: スケジュール作成コマンド
- `recruitment_schedule_list.rs`: スケジュール一覧表示コマンド
- `recruitment_schedule_edit.rs`: スケジュール編集コマンド
- `recruitment_schedule_delete.rs`: スケジュール削除コマンド
- `recruitment_schedule_toggle.rs`: スケジュール有効/無効切り替えコマンド

#### 3.2 スケジューラー統合

**SchedulerFacade** (`facades/scheduler.rs`):

現在の`execute_notifications()`の処理に加えて、新たに定期募集処理を追加：

```rust
pub async fn execute_notifications(&self, http: Arc<Http>) -> Result<()> {
    // 既存の通知実行処理
    self.execute_scheduled_notifications(http.clone()).await?;

    // 新規: 定期募集実行処理
    self.execute_recruitment_schedules(http.clone()).await?;

    Ok(())
}
```

### 5. エラーハンドリング

**想定されるエラー**:
- クエストIDが無効
- バトルスタイルIDが無効
- チャンネルが見つからない
- Discordメッセージ投稿失敗
- DB接続エラー

**対応方針**:
- エラーログを記録（tracing::error）
- 次回実行時にリトライ（last_process_timesは更新しない方針も検討）
- ユーザーには適切なエラーメッセージを返信

### 6. セキュリティ・パフォーマンス考慮事項

**セキュリティ**:
- RLS（Row Level Security）は適用しない（Systemロールで実行）
- 権限チェックはアプリケーション層で実施

**パフォーマンス**:
- スケジュール数が多い場合のN+1問題に注意（JOIN最適化）
- last_process_timesで差分処理を実現し、全スケジュールを毎回計算しない
- Discordメッセージ投稿の並列化（tokio::spawn活用）
