# レイヤード構成（開発者向け）

## 目的

機能追加や修正をしても破綻しにくくし、テストしやすい構造を保つために責務を分離して依存方向を固定します。

## 依存方向（重要）

このプロジェクトは、原則として次の一方向に依存します。

`events → facades → services → repository（port）`

`infrastructure` の具体実装はDIで配線し、Serviceから直接依存しません。

## 各層の責務

- **events（プレゼンテーション層）**
  - Discord入力を受ける
  - 入力検証を行う
  - Facadeを呼び出す
- **facades（アプリケーション層）**
  - ユースケース単位でServiceを組み合わせる
  - トランザクション境界（begin / commit / rollback）を管理する
- **services（ドメイン/業務処理）**
  - 業務ルールを実装する
  - Repository traitにのみ依存する
- **repository（ポート層）**
  - 永続化契約（trait）を定義する
  - ORM固有処理を持たない
- **infrastructure（アダプター層）**
  - Repository traitを実装する（例: SeaORM）
  - DB固有の実装詳細・最適化を担当する

## トランザクション（重要）

- **トランザクションの開始/コミット/ロールバックは Facade 層のみ**
- Serviceは受け取ったトランザクションを下位へ渡す

## 禁止事項（代表）

- events から services / repository を直接呼ぶ
- facades から repository を直接呼ぶ（Service経由にする）
- repositoryアダプターに業務ロジックを書く
- services が `SeaOrm*Repository` など具象型へ依存する
