# スケジュール機能

## 概要

本機能は、`worker.scheduled_tasks` を中核として「指定時刻に処理を実行する」ための共通基盤です。
通知だけでなく、解散、定期募集、自動募集関連タスクを同一の実行モデルで扱います。

## 目的

- 時刻実行処理を `scheduled_tasks` に統一し、実装と運用を単純化する
- 個別機能ごとの実行ロジックを Executor に分離し、拡張しやすくする
- 失敗や欠損データがあっても他タスクへ波及しない実行方式を保つ

## タスク種別

`ScheduledTaskType` の主要種別:

- `1: Notification` 通知送信
- `2: Dissolution` 募集解散
- `3: DataCleanup` データクリーンアップ
- `4: RecurringRecruitment` 定期募集の実行
- `5: Dismissal` 人数不足による解散
- `6: AutoRecruitmentRotation` 自動募集の日付ローテーション
- `7: AutoMatching` 自動マッチング実行

## タスク実行状態（`scheduled_tasks.execution_status`）

タスクの実行状態は PostgreSQL ENUM（`worker.task_execution_status`）で管理します。

- `pending`: 未実行
- `succeeded`: 正常終了
- `succeeded_with_warning`: 正常終了（警告あり）
- `failed`: 異常終了

方針:

- スケジューラの実行対象は `pending` のみ
- `succeeded_with_warning` は「実行完了」として扱い、次回自動再実行はしない
- `failed` は「異常終了」として扱い、次回自動再実行はしない（必要時は別途リカバリ）

## イベント通知スケジュール生成仕様（global/guild統合）

本章は、イベント通知（`task_type = Notification`）を再生成するときの
`global` と `guild` の統合ルールを定義します。

### スケジュール生成に使用するテーブル

イベント通知の生成時に参照するテーブルは次の6つです。

1. `master.event_schedules`（グローバルのイベントスケジュール）
2. `master.event_schedule_details`（グローバルのイベント期間内詳細スケジュール）
3. `master.message_texts`（グローバルのメッセージテキスト）
4. `guild_master.guild_event_schedules`（guild版イベントスケジュール）
5. `guild_master.guild_event_schedule_details`（guild版イベント期間内詳細スケジュール）
6. `guild_master.guild_message_texts`（guild版メッセージテキスト）

### global / guild の同一判定

- `event_schedules` 系: `id` が同じ場合に同一スケジュールとして扱う
- `event_schedule_details` 系: `id` が同じ場合に同一詳細として扱う
- `message_texts` 系: `id` が同じ場合に同一メッセージとして扱う
- ただしイベントスケジュールと詳細の結合に関しては、`profile`が同一かで判断し、イベントスケジュールと詳細の`id`は結合条件としない

### 統合方針

- globalのみ存在: globalデータで通知を生成する
- guildのみ存在: guildデータのみで通知を生成する
- globalとguildの両方が存在: 同一`id`の範囲でguild側を優先して上書きする

### 通知先チャンネル解決処理の優先順位

通知先チャンネルは次の順で解決します。

1. `guild_event_schedule_details.notification_channel_id`
2. `guild_event_schedule_details.notification_channel_type` から `guild_channels` を解決
3. `event_schedule_details.notification_channel_type` から `guild_channels` を解決
4. 1〜3のいずれでも解決できない場合はエラー

前提:

- 本仕様では `guild_event_schedule_details` に `notification_channel_id`（NULL許容）を持つ前提とする
- スキーマ反映前の段階では、`notification_channel_type` ベースの解決のみが有効となる

補足:

- guild詳細で`notification_channel_id`と`notification_channel_type`の両方が設定されている場合は、`notification_channel_id`を優先する
- guild詳細で両方未設定の場合、そのguild向けの当該詳細通知は登録しない（警告ログを出して継続）

### メッセージテキストID解決処理の優先順位

通知行に紐づける `message_text_id` は次の順で解決します。

1. guild詳細に`message_text_id`が定義されていればそれを使用
2. global詳細に`message_text_id`が定義されていればそれを使用
3. 1,2のどちらも解決できない場合はエラー

`message_text_id` 決定後の本文解決（`MessageService` 利用、`guild_message_texts` -> `message_texts` -> `locales/messages.yml` -> エラー）とロケール選択は、[メッセージ解決](./メッセージ解決.md)の仕様に従う。

### スケジュール再生成フロー（通知）

1. 既存の通知系スケジュール（`worker.scheduled_tasks` / `worker.notifications` / `worker.notification_rel_event_schedules`）を初期化
2. global / guild の `event_schedules` を統合
3. global / guild の `event_schedule_details` を統合
4. 統合結果をもとに、guildごとに通知先チャンネルと`message_text_id`を解決
5. 解決できた行のみ `scheduled_tasks` / `notifications` / `notification_rel_event_schedules` を作成
6. エラー行は記録して継続し、処理全体の完了後に集計結果を出力

## イベント通知のエラー制御

### 基本方針

- どのデータで何のエラーが発生したかを識別可能な形で記録する
- エラー行以外のスケジュール生成は継続する

### エラー単位

- `event_schedules`（global / guild）起因: イベントスケジュール行単位
- `event_schedule_details`（global / guild）起因: イベント詳細行単位
- メッセージ未定義起因: イベント詳細行単位
- 通知先未解決起因: イベント詳細行単位（guild単位の文脈を含める）

### エラー時に保持する情報

- `guild_id`（該当する場合）
- `event_schedule_id`
- `event_schedule_detail_id`
- `message_text_id`（解決途中で判明している場合）
- エラー種別（例: `NotificationChannelNotResolved`, `MessageTextNotResolved`）

## パターン一覧（正常）

※ ここで使用している数字（1〜6）は[スケジュール生成に使用するテーブル](#スケジュール生成に使用するテーブル)の番号を指します。
※ 各パターンの記載順は「イベント → 詳細 → メッセージ」です。

- 1,2,3あり、4,5,6なし
  - globalのみのパターン
  - 1,2の日時・通知先に対して3を送信

- 1,2,3,6あり、4,5なし
  - イベント情報はglobal、メッセージのみguildのパターン
  - 1,2の日時・通知先に対して6を送信

- 1,2,3,4,5,6あり
  - guildがglobalを完全に上書きしているパターン
  - 4,5の日時・通知先に対して6を送信

- 1,2,3,4,5あり、6なし
  - guildがglobalを上書きしているが、メッセージテキストはglobalのパターン
  - 4,5の日時・通知先に対して3を送信

- 1,5,3あり、4,2,6なし
  - イベント基準日はglobalだが、内部スケジュールをguildで定義し、メッセージはglobalのパターン
  - 1のイベント日から見た5の日時・通知先に対して3を送信

- 1,5,6あり、2,4,3なし
  - イベント基準日はglobalだが、内部スケジュールをguildで定義し、メッセージもguildのパターン
  - 1のイベント日から見た5の日時・通知先に対して6を送信

- 4,5,6あり、1,2,3なし
  - guild独自のイベントで通知を行うパターン
  - 4,5の日時・通知先に対して6を送信

## パターン一覧（エラー）

- 2または5で決定した`message_text_id`に対応する本文が6,3,`locales/messages.yml`のいずれでも未定義
  - メッセージ内容を解決できないパターン
  - [メッセージ解決](./メッセージ解決.md)を参照
  - メッセージ未解決エラーとして詳細行単位で記録されること

- 2または5（通知先チャンネルID指定なし）でチャンネル種別ID指定があるが、そのguildで対応するguild_channelsの行が存在しない
  - 通知先チャンネルが解決できないパターン
  - [通知先チャンネル解決処理の優先順位](#通知先チャンネル解決処理の優先順位)を参照
  - 解決できるguildのみ通知登録し、解決不能guildはエラー記録して継続すること

## 実行アーキテクチャ

### レイヤー責務

- Events: スケジュール実行トリガー、ログ、例外境界
- Facade: トランザクション境界、Executorの呼び出し協調
- Services: SchedulerManager / 各TaskExecutorの業務ロジック
- Repository: `scheduled_tasks` と各関連テーブルの永続化

### 実行サイクル（10秒間隔）

1. `execution_status = 'pending'` のタスクを取得（過去分 + 現在〜20秒先）
2. `schedule_datetime <= now` のタスクを実行対象として抽出
3. `task_type` ごとに Executor を切り替えて処理
4. 実行結果に応じて `scheduled_tasks.execution_status` を更新（`succeeded` / `succeeded_with_warning` / `failed`）
5. 定期募集など再実行が必要なものは次回タスクを生成

### 整合性方針

- 実行直前にDBを再確認し、無効化・削除済み対象を安全にスキップ
- 個別タスク失敗時はエラーログを出し、該当タスクを `failed` に更新したうえで他タスク処理は継続
- 警告付き完了は `succeeded_with_warning` として記録し、運用上で追跡可能にする
- 同一タスクの重複実行を防ぐため、`execution_status` で状態管理する

## 主要テーブル

| テーブル | 役割 |
| --- | --- |
| `worker.scheduled_tasks` | 実行日時・種別・実行状態を管理する基底テーブル |
| `worker.notifications` | 通知内容（`task_id` で `scheduled_tasks` と1対1） |
| `worker.scheduled_task_dissolutions` | 解散対象募集との関連 |
| `worker.scheduled_task_dismissals` | 人数不足解散対象との関連 |
| `worker.scheduled_task_recurring_recruitments` | 定期募集スケジュールとの関連 |
| `worker.scheduled_task_cleanups` | クリーンアップ対象情報 |

## 代表ユースケース

- イベント通知の再生成と時刻送信
- 定期募集スケジュールからの募集自動作成
- 募集出発時刻での解散判定
- 自動募集（ローテーション/マッチング）の定期実行

## 運用上の注意

- 大量再生成は低負荷時間帯で実施する
- タスク詰まり監視として未実行件数の監視を推奨
- `DataCleanup` の対象は誤設定すると影響が大きいため、対象テーブルを明示管理する
- 通知再生成時は、エラー件数とスキップ件数を必ず記録し、運用者が追跡できるようにする
