# タスク種別7: 自動マッチング（AutoMatching）

## 概要

`task_type = 7` は自動募集参加者の希望条件をマッチングし、  
成立グループの通知と募集作成を行うタスクです。  
対象は全ギルドで、`scheduled_tasks.guild_id` / `channel_id` は `NULL` で管理します。

## 登録フロー

- 初回登録: 自動募集カテゴリ登録時（`category_setup_facade`）
- 再登録: 実行完了時に「10秒後」を次回として自己再登録

初回登録時は pending タスクを確認し、`task_type=7` が既にある場合は重複作成しません。

## scheduler連携時の依存方向

- `SchedulerTaskDispatchFacade` を合成ポイントとし、トランザクション境界を管理しつつ
  `crate::di::Repositories` から受け取ったRepositoryで `PeriodicMatchingService`・
  `AutoMatchingDispatchSupportService`・`RecruitmentCreationService` を組み立てる。
  通知・募集のUI組み立て（`NotificationPresenter`・`RecruitmentPresenter`）とGateway経由の
  送信もfacadeが行う。このロジックは元々service層の`AutoMatchingTaskExecutor`にあったが、
  UI組み立てと複数serviceの合成はfacade層の責務であるため、facadeへ統合した。
- 具象Repository実装は `src/infrastructure/database/repositories/**`（SeaORM実装）に配置する。
- `PeriodicMatchingService`・`AutoMatchingDispatchSupportService`・`RecruitmentCreationService` は
  `crate::repository` 経由のtrait（自動募集・スケジュール・募集作成・マスターデータ）に依存し、
  `SeaOrm*Repository` 具象型へ直接依存しない。
- 依存方向は `scheduler_manager（起動トリガー） -> facade（tx + 合成 + UI + gateway） -> service -> repositoryポート` を維持する。
- 具象アダプターの配置先は `src/infrastructure/database/repositories/**` に統一する。

## 実行フロー

`SchedulerTaskDispatchFacade` が `task_type=7` 分岐（`run_auto_matching_dispatch`）を実行します。

1. タスク存在と `pending` を再確認
2. `PeriodicMatchingService::process_matching` を実行
   - 参加可能時刻 (`auto_recruitment_participants`) と希望クエスト (`user_desired_quests`) を結合
   - `auto_recruitment_match_rules` から `guild_id` 優先でプリセットを解決し、未設定時はグローバル設定（`guild_id=0`）を参照
   - プリセットを必須スロットへ変換し、最小成立グループを構築
   - ルール未設定クエストは従来どおり「2人以上」で候補化
   - `quest_matchings` / `quest_matching_users` を作成
3. 成立マッチングごとに通知送信と募集作成を試行
4. 現在タスクを `succeeded`
5. 次回タスク（10秒後）を作成

## 通知・募集作成の詳細

成立マッチング単位で以下を実行します。

1. ギルド設定 (`auto_recruitments`) とマッチングチャンネルを解決
2. 参加者メンション付き通知を送信（Embed）
3. 月日時間から出発時刻（JST基準、`24..28時` 表記対応）を計算
4. 出発時刻が未来なら募集を作成し、`quest_matchings.recruitment_id` を更新
5. 募集作成に成功した場合は、先に送信した通知を編集して募集投稿へのジャンプリンクを追記

- 募集投稿のUIは `/マルチバトル募集2` と同じ共有生成処理を使う

## 実行状態とエラー制御

- マッチング成立が0件でも `succeeded`（`NoMatches`）
- 通知送信失敗はログ出力のみで募集作成を継続
- 募集作成失敗は該当マッチングのみ失敗として継続
- 実行中の致命的エラーは `SchedulerManager` 側で `failed`

## 実装上の注意

- 出発時刻が過去になったマッチングは募集作成をスキップします。
- クエスト情報や自動募集設定が取得できないギルド/マッチングはスキップします。
- 自己再登録方式のため、タスクチェーンが継続していることを監視対象に含める前提です。
