# 接続とトランザクション

## 概要

本プロジェクトでは、DB接続管理とトランザクション管理を分離し、
レイヤード構成（`events → facades → services → repository`）を維持します。

## 設計の目的

- 接続の乱立を防ぎ、運用時の不具合を減らす
- トランザクション境界を統一し、整合性を保つ
- ORM依存を局所化し、上位層の変更耐性を高める
- 将来的な構成変更に耐える

## 設計原則

### レイヤー責務分離

- Facade: ユースケース実行とトランザクション境界
- Service: 業務ルール実装
- Repository（port）: 永続化契約定義
- Infrastructure adapter: 具体的なDBアクセス実装

### AppStateパターン

- 共有接続は `AppState` が管理する
- 各層でアドホック接続を作らない

### Port / Adapter 分離

- Repository traitは `src/repository/**` に置く
- SeaORM実装は `src/infrastructure/database/repositories/**` に置く
- Serviceはtraitのみに依存する

## 何を守るか

- 接続は `AppState` が管理し、各層が勝手に新規接続しない
- トランザクション境界は Facade 層で管理する
- Service は受け取ったトランザクションを Repository に渡す
- Repositoryアダプターは永続化に集中し、業務判断を持たない

## 主要コンポーネントと責務

### AppState

- アプリ全体で共有するDB接続を保持する
- ユースケースごとの接続取得起点になる

### Facade側トランザクション調停

- トランザクション開始
- 処理結果に応じた commit / rollback
- 失敗時のロールバック保証
- Service実行コンテキストの提供

### Service

- 業務ルールを実装する
- トランザクション開始/終了は行わない

### Repository port

- 永続化操作をtraitメソッドで定義する
- ORM固有APIを含めない

### Infrastructure repository adapter

- トランザクション/接続上でSeaORMクエリを実行する
- Repository traitを実装する

### DBセッション文脈ヘルパー（`src/infrastructure/database/session`）

- セッション文脈設定（例: RLS用セッション変数）を担当する
- 必要な処理ではトランザクション開始直後に設定する
- Service層へセッションSQLを持ち込まない

## 典型的な処理フロー

1. Facade が `AppState` からトランザクションを開始
2. 必要ならFacadeがDBセッション文脈を初期化
3. Facade が複数Serviceを協調して実行
4. Service がトランザクションをRepository traitへ渡す
5. Adapter がDB操作を実行
6. すべて成功なら commit
7. 途中失敗なら rollback

## トランザクション境界の判断基準

- 整合性が必要な更新を同一境界にまとめる
- 外部API呼び出しは可能な限り境界外へ出す
- DBロック保持時間が長くならない単位で区切る

## 失敗時の考え方

- DB更新途中で失敗した場合は rollback し、部分更新を残さない
- 外部I/O（Discord送信など）を含む処理は順序設計と再実行戦略を定義する
- ロールバック失敗は `error` ログで捕捉し、調査可能性を確保する

## トランザクション設計の原則

- 長いトランザクションを避ける
- 外部API待ちをトランザクション内に抱え込まない
- 必要最小限の更新を短時間で完結させる
- 同一ユースケース内でも責務ごとに処理境界を明確化する

## アンチパターン

- events 層で直接トランザクションを開始する
- Service 層で commit / rollback を行う
- Repositoryアダプター層でビジネス分岐を行う
- ServiceにRLS/セッションSQLを書き込む
- 失敗時に rollback せず継続する

## ベストプラクティス

- Facade内で処理順序を固定し、可観測ログを残す
- 重要更新は更新対象の再確認を入れる
- 並行処理はトランザクション外で実施し、更新フェーズを短く保つ

## チェックリスト

- Facade が明示的にトランザクション境界を持っているか
- Service がトランザクション制御をしていないか
- Repository port がORM非依存になっているか
- セッション文脈設定が `infrastructure/database/session` に集約されているか
- 外部I/O失敗時挙動（再試行・補償）が定義されているか
- ロールバック失敗時のログが設計されているか
