# 結合テスト

結合テストは、複数レイヤーをまたぐユースケースの整合性を検証します。
本プロジェクトでは主に **Facade起点** で書きます。

## 配置

- `tests/integration/` 配下
- 例: `tests/integration/facades/`（Facade起点）

## 実DBが必要なテスト

Facade結合テストは testcontainers が用意する実PostgreSQLを使います。
フィクスチャは `tests/integration/facades/test_helper.rs` にあります。

- **コンテナはテストバイナリごとに1つ。** `OnceCell` で1回だけ起動し、そのバイナリ内の全テストで共有する
- **テンプレートDBはコンテナごとに1つ。** 起動直後に、RLSで使うアプリ用DBロールの作成、`pgcrypto` の有効化、
  全マイグレーションの適用、共通マスターデータの投入をテンプレートDBに対して行う。
  複製できるようにするため、この初期化に使った接続は明示的にクローズする
- **データベースはテストごとに1つ。** `create_test_app_state()` は呼び出しのたびに
  `CREATE DATABASE ... TEMPLATE ...` でテンプレートを複製し、その新しいDBに紐づく `AppState` を返す。
  テンプレートの複製はファイルコピーなので、マイグレーションを再実行するより遥かに安価。
  初期化後はテンプレートDBに誰も接続しないため複製は同時実行してよい。
  ここを直列化するだけでスイート全体が4倍遅くなるので、ロックで囲まないこと

テストごとにDBが独立しているため、テスト同士は干渉しません。

- 同じ `guild_id` を複数のテストで使っても衝突しない
- あるテストの絞り込みなし `delete_many()` が他のテストに影響しない
- テストスイートは並列実行できる（`RUST_TEST_THREADS` を 1 に固定する必要がない）

把握しておくべきコスト:

- 複製1件あたり約10MB。フルラン中はコンテナ内に約1.5GBを保持する。
  実行終了時に使い捨てコンテナごと破棄されるため、ホストには残らない
- テストごとに接続プールを持つため、コンテナの `max_connections` を引き上げている。
  同じ理由で1プールあたりの接続数は絞っている（`max_connections(4)` / `min_connections(0)`）
- 接続プールを `static` にキャッシュしてはいけない。`#[tokio::test]` はテストごとに
  ランタイムを作って終了時に破棄するため、最初のテスト中に作ったプールはそのテストの終了と同時に
  使えなくなる。フィクスチャは `CREATE DATABASE` のたびに短命の管理接続を張り直している

テスト内のクリーンアップは、前提条件を明示する意味では引き続き有用ですが、
テストの独立性を担保しているのはもはやクリーンアップではありません。

`#[ignore]` は外部シークレットや外部APIを必要とするテストのためのものです。
「PostgreSQLが必要だから」という理由だけで付けてはいけません。

### 同じデータベースへ複数の接続を取る場合

`create_test_app_state()` は呼び出すたびに**新しい**データベースを作るため、
1つのテスト内で2回呼ぶと互いに無関係な2つのDBができてしまいます。
Facade呼び出しに加えてRLS検証用のロール別接続が要る場合など、
複数の接続が必要なときは先に `TestDb` ハンドルを取得し、そこから全ての接続を導出してください。

```rust
let test_db = TestDb::new().await;
let app_state = Arc::new(test_db.app_state().await);
let guild_role_db = test_db.guild_role_db().await; // app_state と同一のDB
```

| メソッド | ロール | 用途 |
| --- | --- | --- |
| `TestDb::app_state()` | `postgres` | Facade呼び出し用の `AppState`（RLSは適用されない） |
| `TestDb::guild_db()` | `postgres` | データ準備・検証のための直接接続 |
| `TestDb::guild_role_db()` | `gbf_bot_guild` | RLS（`set_current_guild_id`）の挙動検証用 |
| `TestDb::admin_db()` | `gbf_bot_admin` | 管理者ロールが必要な操作用 |

## CI実行

- 通常のテストレーンは、PostgreSQLサービスコンテナもDB認証情報も無しでFacade結合テストを実行する
- テストフィクスチャがPostgreSQLコンテナを起動できるよう、ランナーはDockerアクセスを許可している必要がある
- 外部シークレットが必要なテストは引き続き ignore され、専用ワークフローでのみ実行する

## データの扱い

- テストの意図が伝わる、そのテスト専用の `guild_id` / `user_id` を使う
- クリーンな初期状態に依存するテストでは、対象データを明示的に削除する

## 設計メモ

- 1テスト = 1目的（巨大化させない）
- 失敗時に「何が壊れたか」が分かるアサーションにする
