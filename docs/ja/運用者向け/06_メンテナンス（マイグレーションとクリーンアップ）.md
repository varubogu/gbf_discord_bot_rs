# メンテナンス（マイグレーションとクリーンアップ）

この章は、運用者が「DB構造の更新」と「古いデータの削除」を安全に実施するための手順です。

## マイグレーション（DBの更新）

Botの機能追加でDB構造が変わることがあります。通常はBot更新のタイミングで実施します。

### いつ実行する？

- Bot更新直後（または更新前）にDB更新が必要と案内されたとき
- 新機能がDBを必要とするのに動かないとき

### 実行コマンド

- `cargo run -- migrate`

## データクリーンアップ（古いデータの削除）

古い募集・通知・タスクを削除し、DB容量増加や性能劣化を抑える運用です。
Bot本体とは分離したメンテナンス経路で実行します。

### 概要

- 既定では30日より古い対象データを削除
- メンテナンス用コンテナで実行（Bot本体と分離）
- 専用DBロール（`gbf_bot_cleanup`）で最小権限運用
- `maintenance_scheduler` が常駐し、UTC指定時刻に日次実行

### いつ実行する？

- 毎日深夜など、利用が少ない時間帯（推奨）
- DB容量が増え続けているとき

## 前提条件

- `.env.maintenance` が設定済み
- PostgreSQL が稼働中
- クリーンアップ実行ユーザー（`gbf_bot_cleanup`）が作成済み

## 実行方法

### 開発環境

- `cargo run --bin cleanup`

### 環境変数を直接指定して実行する場合

- `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` を指定
- `CLEANUP_RETENTION_DAYS` を必要に応じて上書き

### 本番環境（Docker Compose）

`./mng.sh prod up` で `maintenance_scheduler` が自動起動します。

### 手動で1回だけ実行

- `docker compose run --rm maintenance`
- `docker compose run --rm -e CLEANUP_EXECUTION_MODE=once maintenance`

### 一時的に保持期間を変更して実行

- `docker compose run --rm -e CLEANUP_RETENTION_DAYS=60 maintenance`

## 定期実行設定（コンテナ内スケジューラー）

`.env.maintenance` で日次実行時刻を調整できます:

- `CLEANUP_SCHEDULE_HOUR_UTC`（既定 `3`）
- `CLEANUP_SCHEDULE_MINUTE_UTC`（既定 `0`）
- `CLEANUP_RUN_ON_STARTUP`（既定 `false`）

補足:

- 深夜帯（例: 03:00 UTC）での実行を推奨
- ログローテーションを設定し、ログ肥大化を防止

## 削除対象データ

### 1. `worker.battle_recruitments`

- 削除条件: クエスト開始日時が保持期間より古い かつ 募集終了済み
- 外部キー連鎖で関連データ（参加者・解散設定・通知関連）も削除

### 2. `worker.notifications`

- 削除条件: 通知予定日時が保持期間より古い かつ 送信済み
- 外部キー連鎖で通知関連テーブルも削除

### 3. `worker.scheduled_tasks`

- 削除条件: 実行予定日時が保持期間より古い かつ 実行済み かつ `DataCleanup` 以外
- 外部キー連鎖でタスク関連テーブルも削除

## 保持期間

- 既定: `CLEANUP_RETENTION_DAYS=30`
- 恒久変更: `.env.maintenance` を更新

## 失敗時の挙動

- クリーンアップ中の失敗時はトランザクションをロールバック
- 途中まで削除された状態は残さない

## 監視とログ

- 実行開始・基準日時・削除件数・完了/失敗をログで確認
- 確認コマンド例:
  - `tail -f /var/log/gbf-cleanup.log`
  - `docker compose logs -f maintenance_scheduler`
  - `docker compose logs maintenance`

### デバッグ実行

- `docker compose run --rm -e RUST_LOG=debug maintenance`

## 注意事項

- 同時多重実行は避ける（冪等性があっても運用負荷が増える）
- 削除データは復元不可のため、定期バックアップを必須化する
- 本番で保持期間を変える場合は、事前に合意を取ってから反映する
- 手動実行前に、`maintenance_scheduler` と実行重複しないことを確認する
