# Schema Management

## Overview

This project uses multiple PostgreSQL schemas (`master` / `guild_master` / `worker`).
Because spreadsheet integration and generic repositories must “resolve schema name from table name”, we systematize mapping management and verification.

## What can go wrong

- When tables are added/moved, schema resolution isn’t updated and runtime errors occur
- Naming conventions degrade, making it unclear “what lives in which schema”
- Divergence between code and docs leads to wrong maintenance decisions

## Management policy

1. Centralize schema-name resolution logic in a shared module
2. Auto-generate the mapping table at build time from entity definitions
3. Continuously verify consistency with `schema_lint`
4. Treat `src/models/entities` as the primary source of truth

## Schema resolution structure

- Entry point: `services/spreadsheet/schema_utils`
- Role: resolve schema name from table name and return schema-qualified references
- Expectation: callers can reference tables without knowing schema details

## Build-time generation

The schema mapping table is generated at build time based on entity attributes (`schema_name` / `table_name`).

Flow:

1. `build.rs` analyzes entity definitions
2. Extracts each entity’s `schema_name` / `table_name`
3. Outputs generated code for the mapping table
4. At runtime, loads and uses the generated code

Therefore, when adding entities, the most important thing is defining entity attributes correctly.

## Consistency verification with `schema_lint`

### Command

```bash
cargo run -j 1 --bin schema_lint
```

### What it checks

- Naming convention and schema placement consistency
- Validity of exception rules (e.g., `guild_last_process_times`)
- Visibility of table lists per schema

### In CI

- Operate with the assumption that `schema_lint` is part of CI
- For changes that add/move entities, run it before merging

## Schema design rules

### `master`

- Master/reference data shared across the app
- Examples: quests, strategies, elements, shared messages

### `guild_master`

- Per-guild settings and master/reference data
- Examples: channel settings, guild environment variables, per-guild spreadsheet settings

### `worker`

- Runtime work data and state management
- Examples: recruitment history, notifications, scheduled tasks

## Checklist when updating

- Defined `schema_name` / `table_name` on new entities
- Checked the impact scope when moving existing tables
- Ran `schema_lint` and confirmed no errors
- Confirmed consistency with the table design docs

## Troubleshooting

### Schema info is missing after build

- Check for missing entity attribute definitions
- Check where generated code is imported and how modules reference it
- Re-check after a clean build

### `schema_lint` reports violations

- First check schema definitions on the entity side
- If it’s a design exception, reflect it in lint exception rules
- When adding exceptions, document the reason in the table design docs
