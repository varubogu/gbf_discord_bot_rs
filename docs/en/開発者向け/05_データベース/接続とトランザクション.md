# 接続とトランザクション

## 概要

本プロジェクトでは、DB接続管理とトランザクション管理を分離し、
レイヤード構成（`events → facades → services → repository`）を崩さずに運用します。

## 設計の目的

- 接続の乱立を防ぎ、運用時の不具合を減らす
- トランザクション境界を統一し、整合性を保つ
- 実装詳細（ORM）への依存を局所化する
- 将来的な構成変更に耐える

## 設計原則

### ORM非依存性

- トランザクション抽象化（`DatabaseTransactionTrait`）
- 接続抽象化（`DatabaseConnectionTrait`）
- ORM固有型への直接依存を上位層に持ち込まない

### レイヤー責務分離

- Facade: ユースケース実行とトランザクション境界
- Service: 業務ルール実装
- Repository: 永続化

### AppStateパターン

- 共有接続は `AppState` 管理
- 各層でアドホック接続を作らない

## 何を守るか

- 接続は `AppState` が管理し、各層が勝手に新規接続しない
- トランザクション境界は Facade 層で管理する
- Service は受け取ったトランザクションを Repository に渡すだけにする
- Repository は永続化処理に集中し、業務判断を持たない

## 主要コンポーネントと責務

### AppState

- アプリ全体で共有するDB接続を保持
- ユースケースごとの接続取得起点

### TransactionManager（Facade側の調停役）

- トランザクション開始
- 処理結果に応じた commit / rollback
- 失敗時のロールバック保証
- Repository群の利用コンテキストを提供

### TransactionContext

- トランザクション実体とRepositoryアクセスをまとめた実行文脈
- FacadeがServiceを協調実行する際の共通コンテナ

### Service

- 業務ルールを実装
- トランザクション開始・終了は行わない

### Repository

- トランザクション内でのクエリ実行
- CRUD処理の一貫性維持

## 典型的な処理フロー

1. Facade がトランザクションを開始
2. Facade が複数Serviceを協調して実行
3. Service が Repository にトランザクションを渡す
4. すべて成功なら commit
5. 途中失敗なら rollback

## トランザクション境界の判断基準

- 1ユースケースで整合性を保証したい更新を同一境界にまとめる
- 外部API呼び出しは可能な限り境界外へ出す
- DBロック保持時間が長くならない単位で区切る

## 失敗時の考え方

- DB更新途中で失敗した場合は rollback し、部分更新を残さない
- 外部I/O（Discord送信など）を含む処理は、順序設計と再実行戦略を必ず定義する
- ロールバック失敗は別途 `error` ログで捕捉し、調査可能性を確保する

## トランザクション設計の原則

- 長いトランザクションを避ける
- 外部API待ちをトランザクション内に抱え込まない
- 必要最小限の更新を短時間で完結させる
- 同一ユースケース内でも責務ごとに処理境界を明確化する

## アンチパターン

- events 層で直接トランザクションを開始する
- Service 層で commit / rollback を行う
- Repository 層でビジネス分岐を行う
- 失敗時に rollback せず継続する

## ベストプラクティス

- Facade内で処理順序を固定し、可観測ログを残す
- 重要更新は「更新対象の再確認」を入れる
- 並行処理はトランザクション外で前処理し、更新フェーズは短く保つ

## チェックリスト

- Facade が明示的にトランザクション境界を持っているか
- Service がトランザクション制御をしていないか
- Repository がDB操作に集中しているか
- 外部I/Oの失敗時挙動（再試行・補償）が定義されているか
- ロールバック失敗時のログが設計されているか
