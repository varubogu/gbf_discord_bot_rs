# 結合テスト設計方針

## 概要

結合テストは、複数レイヤーをまたぐユースケースの整合性を検証するためのテストである。
本プロジェクトでは、`events -> facades -> services -> repository` の依存方向を前提に、主に `Facade` を起点としてテストする。

## ルールを適用するディレクトリ

- `tests/`

## 主な対象

- `Facade` を入口としたユースケース
- `Service` と `Repository` の連携結果
- トランザクション境界の妥当性（開始・コミット・ロールバック）
- 永続化結果（作成・更新・検索・削除）

## 対象外

- 関数単体の分岐網羅（単体テストで実施）
- Discord API 外部サービス実体との疎通（E2Eテストで実施）
- 性能測定や負荷検証（性能テストで実施）

## 配置方針

- 結合テストは `tests/integration/` 配下に配置する。
- 機能単位でディレクトリを分割し、`facades` を中心に整理する。
- 1ファイル1責務を基本とし、過度に巨大なテストファイルを避ける。

## 設計原則

### 1. Facade起点

- 結合テストの主入口は `Facade` とする。
- `events` 層はI/O依存が強いため、結合テストでは直接の対象にしない。
- `Repository` 直接呼び出しの検証は、必要最小限の確認に限定する。

### 2. 実DB利用

- `Repository` を含む経路の確認には実DBを利用する。
- テスト専用データを投入し、テスト内で完結させる。
- 共有データに依存しない（テスト順序に依存しない）構成にする。

### 3. トランザクション境界の検証

- トランザクション開始・終了は `Facade` の責務であることを前提に検証する。
- 異常系ではロールバック後の永続化状態を確認する。
- 長時間トランザクションを避け、1ユースケース1トランザクションを原則とする。

### 4. 振る舞い検証優先

- 内部実装の詳細ではなく、入力と出力、および永続化結果を検証する。
- テストは AAA（Arrange-Act-Assert）で記述する。
- アサーションは「業務上意味のある結果」に絞る。

## テストデータ管理

- テストごとに一意な `guild_id` / `user_id` などを使用する。
- 前処理で対象テーブルを明示的にクリーンアップする。
- 後処理でも同様にクリーンアップし、再実行可能性を担保する。
- `Utc::now()` 依存の判定は避け、必要に応じて固定値を使う。

## テストケース設計

各ユースケースで最低限以下を持つ。

1. 正常系: 想定入力で成功し、永続化結果が期待通りである。
2. 業務異常系: ドメイン制約違反時に期待エラーとなる。
3. 前提欠如異常系: 必須前提データがない場合の失敗を検証する。
4. 冪等性/重複系: 同一操作の再実行時の扱いを検証する。

## 実行ルール

- 実DB必須テストには `#[ignore]` を付与し、通常の高速テストと分離する。
- `migrate up` はテスト実行コマンド単位で開始時に1回だけ実施する。
- データクリーンアップはテストケース単位で実施する（前処理と後処理の両方）。
- ローカルでは対象機能の結合テストを優先実行し、最後に全体を実行する。
- 失敗時はデータ汚染の有無を確認し、再現手順を固定化する。

## テストDB環境設計（1ホスト・複数DB）

- テスト用DBは1つのPostgreSQLホストに複数データベースを作成して運用する。
- 各ワーカーに1つのDBを固定割り当てし、同一DBへの同時書き込みを避ける。
- DB名は `test_db_01` 形式で連番管理する。
- マイグレーションは全テスト開始前に全DBへ適用する。

### クリーンアップ単位

- クリーンアップの責務はテストケース単位とする。
- 各テストは `Arrange` 前に対象テーブルを明示的に初期化する。
- 各テストは `Assert` 後にも初期化を実施し、再実行可能性を担保する。
- テスト実行全体の終了時クリーンアップは補助的な保険として扱い、主手段にしない。

### ワーカー数上限の設計

- 上限は「利用可能テストDB数」「DB接続上限」「CPUコア数」の最小値で決める。
- 推奨値は次の式で算出する。
- `max_workers = min(test_db_count, cpu_cores, floor(db_max_connections / connections_per_worker))`
- `connections_per_worker` は `pool.max_connections + 余裕分` として見積もる。
- 初期値は `test_db_count` と同値にし、接続枯渇や待機が出たら段階的に下げる。

## 禁止事項

- `events` から `services` / `repository` へ直接到達する経路を前提にしたテスト
- テスト間で状態を引き継ぐ前提の設計
- 外部時刻・外部環境差分に依存した不安定なアサーション
- 結合テストで `unwrap()` 前提のエラーハンドリングを行うこと

## 命名規約

- ファイル名は `{feature}_test.rs` を基本とする。
- テスト関数名は `test_{use_case}_{expected}` 形式を推奨する。
- ケース番号管理が必要な場合は、コメントで `1-1`, `1-2` のように明示する。
