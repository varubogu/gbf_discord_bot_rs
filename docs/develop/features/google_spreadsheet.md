# Googleスプレッドシート連携機能

## 概要

Googleスプレッドシートを使用してPostgreSQLデータベースとの双方向データ同期を実現する機能です。マスターデータやギルド固有設定をスプレッドシートで管理し、Botと同期できます。

## 目的

- **データ管理の簡易化**: SQLを書かずにスプレッドシートでデータ管理
- **非エンジニアでも編集可能**: 表計算ソフトの操作だけでBotの設定変更が可能
- **バックアップとバージョン管理**: Googleドライブの版履歴機能を活用
- **データの可視化**: スプレッドシートでデータを視覚的に確認・編集

## 機能分類

本機能は2種類のスプレッドシート連携を提供します：

### 1. グローバルスプレッドシート連携

**用途**: 全ギルド共通のマスターデータ管理

- **対象データ**: battle_types、quests、elements、messagesなど
- **実行権限**: Bot管理者専用サーバーのみ
- **影響範囲**: 全ギルド
- **コマンド**:
  - `/gspread_global_load` - スプレッドシート → PostgreSQL
  - `/gspread_global_push` - PostgreSQL → スプレッドシート

### 2. ギルドスプレッドシート連携

**用途**: ギルド固有のカスタムデータ管理

- **対象データ**: guild_messages、guild_event_schedulesなど（ギルド固有データ）＋ スプレッドシート設定テーブル（guild_spreadsheet_imports / guild_spreadsheet_exports）
- **実行権限**: gbf_bot_controlロール保持者
- **影響範囲**: 実行したギルドのみ
- **コマンド**:
  - `/gspread_regist` - ギルド用スプレッドシート登録
  - `/gspread_load` - スプレッドシート → PostgreSQL
  - `/gspread_push` - PostgreSQL → スプレッドシート

## 主要ユースケース

### ユースケース1: クエスト情報の一括登録

**シナリオ**: 新しいマルチバトルクエストが追加された

1. Bot管理者がグローバルスプレッドシートの「クエスト情報」シートを編集
2. 新クエストの情報（名前、募集人数、デフォルト戦術）を追加
3. `/gspread_global_load`コマンドを実行
4. 全ギルドで新クエストが利用可能になる

### ユースケース2: ギルド固有のイベントスケジュール設定

**シナリオ**: 特定ギルドが独自のイベント通知スケジュールを設定したい

1. ギルド管理者がギルド固有スプレッドシートの「ギルドイベントスケジュール」シートを編集
2. 独自の通知タイミングや通知先チャンネルを設定
3. `/gspread_load`コマンドを実行
4. 当該ギルドのみでカスタムスケジュールが有効になる

### ユースケース3: メッセージテンプレートのカスタマイズ

**シナリオ**: ギルドの雰囲気に合わせてBotのメッセージを変更したい

1. ギルド管理者がギルド固有スプレッドシートの「ギルドメッセージ定義」シートを編集
2. 特定メッセージIDの文言を変更
3. `/gspread_load`コマンドを実行
4. 当該ギルドのみでカスタムメッセージが表示される

### ユースケース4: データのバックアップ

**シナリオ**: 現在のデータベース状態をスプレッドシートに保存したい

1. `/gspread_global_push`または`/gspread_push`コマンドを実行
2. PostgreSQLのデータがスプレッドシートに書き込まれる
3. Googleドライブの版履歴機能でバックアップが保存される

### ユースケース5: ギルド初期セットアップでのスプレッドシート登録

**シナリオ**: 新しくBotを導入したギルドがスプレッドシート連携を開始したい

1. ギルド管理者がGoogleスプレッドシートを用意し、サービスアカウントに閲覧権限を付与
2. `/gspread_regist`コマンドでスプレッドシートURLを登録
3. `guild_spreadsheet_imports`と`guild_spreadsheet_exports`にスプレッドシートIDが保存される
4. `/gspread_load`や`/gspread_push`で同期が可能になる

### ユースケース6: UUID型IDの自動採番

**シナリオ**: クエスト情報をスプレッドシートに新規追加する際、IDを手動入力したくない

1. Bot管理者がグローバルスプレッドシートの「クエスト情報」シートで新規行を追加
2. `quest_id`列（UUID型）を**空欄のまま**、クエスト名や募集人数などを入力
3. `/gspread_global_load`コマンドを実行
4. Bot側で自動的に新規UUIDが生成され、データベースに登録される
5. **生成されたUUIDがスプレッドシートにも自動的に書き込まれる**
6. 次回読み込み時、同じUUIDが使用され、データの整合性が保たれる

**メリット**:
- UUIDを手動でコピー＆ペーストする必要がない
- スプレッドシートとデータベースのIDが常に一致
- 主キー重複エラーのリスクがゼロ

## スプレッドシート構成

### 「テーブル名」シート（メタ情報）

すべてのスプレッドシートは「テーブル名」という特殊シートを持ち、どのテーブルを同期するかを定義します。

| 行/列 | 内容 | 備考 |
|-------|------|------|
| 1行目 | `sheet_name`, `table_name`, `table_scope`, `table_io`, `table_type` などのマッピングキー | スネークケースで記述 |
| 2行目 | 各列の日本語説明 | プログラムでは使用しない |
| 3行目以降 | テーブル定義データ | 必須列が空の場合はスキップ |

- `table_io`: `"in"`, `"out"`, `"in,out"`（または `"out,in"` / `"both"`）
- `table_type`: `"reference"`, `"transaction"`, `"history"`
- `table_scope`: 将来拡張用（未使用なら空でも可）
- 未定義のキー名が含まれていても無視されるため、柔軟に列を追加できる
- 列順は不問（キー名でマッピング）

**table_io の意味**:
- `in` - スプレッドシート → PostgreSQL（読み込み専用）
- `out` - PostgreSQL → スプレッドシート（書き込み専用）
- `in,out` - 双方向（読み書き両対応）

### 各テーブルシート

テーブルごとに1シートを作成します。

**シート構造**:
- **1行目**: カラム物理名（PostgreSQLと完全一致、キー名でマッピング）
- **2行目**: カラム日本語名（任意、プログラムでは未使用）
- **3行目以降**: データ行（説明行を使用する場合は必ず3行目以降にデータを配置）

列順は問わず、1行目のカラム名で対応付ける。未定義列は自動的に無視する。

**例: questsシート**

| target_id | recruit_count | quest_name | use_battle_type | default_battle_type |
|-----------|--------------|-----------|----------------|-------------------|
| クエストID | 募集人数 | クエスト名 | 使用可能戦術 | デフォルト戦術 |
| 1 | 30 | プロトバハムートHL | 1,2,3 | 1 |
| 2 | 18 | アルティメットバハムートHL | 1,2 | 2 |

## データ同期の優先順位

ギルド固有データとグローバルデータが両方存在する場合、**ギルド固有データが優先**されます。

```
データ参照時の優先順位:
1. ギルド固有テーブル（guild_*）を検索
2. 存在しない場合、グローバルテーブル（*）を検索
3. どちらにも存在しない場合、デフォルト値またはエラー
```

**例: メッセージ取得**
- ギルドAが`guild_messages`に`welcome_message`を定義 → ギルドA独自のメッセージを表示
- ギルドBが定義していない → グローバルの`messages`の`welcome_message`を表示

## 権限管理

### グローバルスプレッドシート

- **実行可能者**: Bot管理者専用サーバーの参加者
- **環境変数**: `BOT_ADMIN_SERVER_ID`で指定されたサーバー
- **レスポンス**: 通常メッセージ（他の管理者も確認可能）

### ギルドスプレッドシート

- **実行可能者**: gbf_bot_controlロール保持者
- **レスポンス**: 通常メッセージ（デフォルト）

## `/gspread_regist` コマンド設計

ギルドごとの読み込み用/書き込み用スプレッドシートIDを専用テーブル（`guild_spreadsheet_imports`, `guild_spreadsheet_exports`）に登録し、`/gspread_load`および`/gspread_push`を実行するための前提条件を整える。

### 目的

- Bot導入直後のギルドでもUI操作のみでスプレッドシート連携を開始できるようにする
- `GLOBAL_SPREADSHEET_ID`のギルド版をDB管理し、環境変数の乱立を防ぐ
- スプレッドシート権限ミスを早期検知し、実行前に通知する

### コマンド仕様

| 引数 | 型 | 必須 | 説明 |
|------|----|------|------|
| `load_spreadsheet_url` | String (最大512文字) | ✅ | ギルドデータ読み込みに利用するGoogleスプレッドシート。IDのみの入力も許可し、正規化後に`guild_spreadsheet_imports`へ保存。 |
| `push_spreadsheet_url` | String (最大512文字) | ✅ | ギルドデータ書き込みに利用するGoogleスプレッドシート。同一シートを使う場合は`load_spreadsheet_url`と同じ値を指定。 |

### 処理フロー

1. **権限チェック**: `gbf_bot_control`ロールを保持しているか検証
2. **guild_id取得**: コマンド実行ギルドのIDを取得（DM禁止）
3. **URL正規化**:
   - 両URL/IDとも`https://docs.google.com/spreadsheets/d/{id}`形式へ正規化
   - 正規表現`^[A-Za-z0-9-_]{20,80}$`で`spreadsheet_id`を検証
4. **権限確認**:
   - 2つの`spreadsheet_id`それぞれに対しGoogle Sheets APIの`spreadsheets.get`を発行
   - 403/404の場合は共有設定不足としてユーザーへ案内
5. **Facade処理** (`GuildSpreadsheetRegistrationFacade`):
   - `TransactionManager`でトランザクション開始
   - `GuildSpreadsheetConfigService`が `guild_spreadsheet_imports` と `guild_spreadsheet_exports` に対し `upsert(guild_id, spreadsheet_id)` を実行
   - 片方のみ更新したい要件に備え、Facadeは引数の差異を検知して必要分のみ更新
   - コミット後に正規化済みURLを含むレスポンスを生成
6. **レスポンス**:
   - 成功: `✅ ギルドスプレッドシートを登録しました`と両URLを表示
   - 失敗: `PresentationError`を通じて日本語メッセージ化

### バリデーションとエラー

- **URL形式エラー**: `❌ エラー: GoogleスプレッドシートのURL形式が正しくありません`
- **共有権限不足**: `❌ エラー: サービスアカウントに閲覧権限がありません。Googleスプレッドシートの共有設定を確認してください`
- **DB書き込み失敗**: リトライ不可のため即時ロールバックし、`❌ ギルド設定の保存に失敗しました`を返す
- **同時実行**: PK(`guild_id`)で自然排他されるが、Facade側で`INSERT ... ON CONFLICT`を利用して冪等性を担保

### データ永続化

- テーブル: `guild_spreadsheet_imports`（読み込み用）
- テーブル: `guild_spreadsheet_exports`（書き込み用）
- いずれも `guild_id` をPK、`spreadsheet_id`を値として保持（最小構成）

### 他コマンドとの関係

- `/gspread_load`は`guild_spreadsheet_imports`を必須依存とし、未登録時は`/gspread_regist`実行を促す
- `/gspread_push`は`guild_spreadsheet_exports`を必須依存とし、未登録時はエラー応答で登録を案内
- 将来的に閲覧用コマンドを追加し、両テーブルの内容を管理者が確認できるようにする

## 認証方式

Google Cloud Platform（GCP）のサービスアカウントを使用したOAuth2認証を採用します。

**必要な環境変数**:
```bash
GOOGLE_SERVICE_ACCOUNT_KEY_FILE=/path/to/service-account-key.json
```

**必要なGoogleスコープ**:
- `https://www.googleapis.com/auth/spreadsheets`

## エラーハンドリング

### エラー時の動作

- **スプレッドシート接続失敗**: コマンド実行を中断、ユーザーにエラーメッセージ表示
- **データ変換エラー**: エラー行をスキップし、ログに記録、処理は継続
- **データベースエラー**: トランザクションをロールバック、全変更を破棄

### エラーメッセージ例

```
❌ エラー: このコマンドはBot管理者専用サーバーでのみ実行可能です

❌ エラー: Googleスプレッドシートへの接続に失敗しました
詳細はログを確認してください

❌ エラー: データ変換中にエラーが発生しました
- questsテーブル 5行目: recruit_count は数値である必要があります
```

## パフォーマンス考慮事項

- **バルクインサート**: 1行ずつではなく一括でデータベースに投入
- **並行処理**: 独立したテーブルは並行で処理
- **トランザクション**: 全テーブルの更新を1トランザクションで実行（全成功or全失敗）

## セキュリティ

- **サービスアカウントキー**: ファイルシステム権限で保護（600推奨）
- **スプレッドシートURL**: 環境変数で管理、ログに出力しない
- **SQLインジェクション**: SeaORMのパラメータバインディングで防止
- **機密情報のマスキング**: エラーログに機密情報を含めない

## 制約事項

### 現在の制約

- **全件同期のみ**: 差分更新は未対応（将来対応予定）
- **リアルタイム同期なし**: コマンド実行時のみ同期
- **スプレッドシート数制限**: グローバル1つ、ギルドごとに1つ

### 推奨される運用

- **小規模データ**: 数千行程度までのデータを推奨
- **定期的なバックアップ**: `/gspread_push`で定期的にスプレッドシートに書き出し
- **変更履歴の確認**: Googleドライブの版履歴機能を活用

## FAQ

### Q1: グローバルスプレッドシートとギルドスプレッドシートの使い分けは？

**A**: 全ギルド共通のマスターデータ（クエスト情報、戦術定義など）はグローバルスプレッドシート、ギルド独自のカスタマイズ（メッセージ文言、イベントスケジュールなど）はギルドスプレッドシートを使用します。

### Q2: データ変換エラーが発生した行はどうなる？

**A**: エラー行はスキップされ、ログに記録されます。他の正常な行は処理されます。ユーザーにはエラー発生行数とエラー内容が表示されます。

### Q3: トランザクションはどのタイミングでコミットされる？

**A**: 全テーブルのデータ投入が成功した時点でコミットされます。途中でエラーが発生した場合、全変更がロールバックされます。

### Q4: スプレッドシートURLはどこで管理する？

**A**: グローバルスプレッドシートは環境変数で管理します。ギルドスプレッドシートは専用テーブル（guild_spreadsheet_imports / guild_spreadsheet_exports）で管理し、環境変数はフォールバック用途に限定します。

### Q5: 既存データは上書きされる？

**A**: はい。`/gspread_load`実行時、該当テーブルのデータは一度削除され、スプレッドシートのデータで置き換えられます（TRUNCATE + INSERT）。

### Q6: 複数人が同時に実行したらどうなる？

**A**: トランザクションにより排他制御されますが、コマンドの実行順序により最後の実行結果が反映されます。運用ルールで同時実行を避けることを推奨します。

### Q7: UUID型のIDが空欄の場合、どうなる？

**A**: Rust側で自動的に新規UUID（UUIDv4）が生成され、データベースに登録されます。さらに、生成されたUUIDはスプレッドシートにも自動的に書き込まれるため、次回読み込み時も同じUUIDが使用されます。

### Q8: UUID書き戻しに失敗したらどうなる？

**A**: データベースへの登録もロールバックされ、エラーメッセージが表示されます。これにより、スプレッドシートとデータベースの整合性が保たれ、次回読み込み時のPK重複エラーを防ぎます。
