# スキーマ管理

## 概要

本プロジェクトは PostgreSQL の複数スキーマ（`master` / `guild_master` / `worker`）を利用します。
スプレッドシート連携や汎用Repositoryでは「テーブル名からスキーマ名を解決」する必要があるため、対応表の管理と検証を仕組み化しています。

## 何が問題になるか

- テーブル追加・移動時にスキーマ解決が更新されず、実行時エラーになる
- 命名規則が崩れ、運用時に「どのスキーマに何があるか」が不明瞭になる
- コードとドキュメントの齟齬で保守判断を誤る

## 管理の基本方針

1. スキーマ名解決ロジックは共通モジュールに集約する
2. Entity 定義からビルド時に対応表を自動生成する
3. `schema_lint` で整合性を継続検証する
4. 一次情報は `src/models/entities` を優先する

## スキーマ解決の構成

- 利用入口: `services/spreadsheet/schema_utils`
- 役割: テーブル名からスキーマ名を解決し、スキーマ修飾付きの参照を返す
- 期待値: 呼び出し側がスキーマの詳細を知らなくても同じ規約で参照できる

## ビルド時自動生成

スキーマ対応表は、Entity の属性（`schema_name` / `table_name`）を元にビルド時に生成されます。

処理の流れ:

1. `build.rs` が Entity 定義を解析
2. 各 Entity の `schema_name` / `table_name` を抽出
3. 対応表の生成コードを出力
4. 実行時は生成済みコードを読み込み利用

このため、Entity 追加時は「Entity 属性を正しく定義する」ことが最重要です。

## `schema_lint` による整合性検証

### 実行コマンド

```bash
cargo run --bin schema_lint
```

### 主な検証観点

- 命名規則とスキーマ配置の整合
- 例外ルール（例: `guild_last_process_times`）の妥当性
- スキーマごとのテーブル一覧の可視化

### CIでの扱い

- `schema_lint` は CI に含める前提で運用する
- Entity 追加・移動を伴う変更では必ず実行してからマージする

## スキーマ設計ルール

### `master`

- 全体共通のマスタデータ
- 例: クエスト、戦術、属性、共通メッセージ

### `guild_master`

- ギルド単位の設定・マスタデータ
- 例: チャンネル設定、ギルド環境変数、ギルド別スプレッドシート設定

### `worker`

- 実行時ワークデータ・状態管理
- 例: 募集実績、通知、スケジュールタスク

## 更新時チェックリスト

- 新規 Entity に `schema_name` / `table_name` を定義したか
- 既存テーブル移動時に参照先の影響範囲を確認したか
- `schema_lint` を実行し、エラーなしを確認したか
- テーブル設計書（別紙）と整合しているか

## トラブルシューティング

### ビルド後にスキーマ情報が見つからない

- Entity の属性定義漏れを確認
- 生成コードの取り込み先とモジュール参照を確認
- クリーンビルド後に再確認

### `schema_lint` で違反が出る

- まず Entity 側のスキーマ定義を確認
- 設計上の例外なら lint 側の例外規則に反映
- 例外追加時は理由をテーブル設計書へ明記
